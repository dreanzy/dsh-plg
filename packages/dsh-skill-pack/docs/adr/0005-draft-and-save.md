# 开关改动先落草稿，保存时才提交

> **状态：已废弃。** 侧栏面板已移除，设置页改为每次改动即时写入，草稿与「保存 / 撤销」不再存在。保留本文只为记录当时的权衡。
>
> 「编辑与提交分开」这一层在 [0007](./0007-pending-changes-and-dry-run.md) 里复活了，但它放弃的理由（预览要在客户端重算求值链）已经不成立：预览改由服务端的 `dryRun` 试算提供。

## 背景与决定

服务端写入本身不会冲突：客户端提交的是绝对状态意图，服务端在文件锁内读—改—写，不比对任何版本。问题出在客户端——如果每拨一次开关就发一次请求、再拿响应整体替换视图，快速连点时会有多个请求同时在途，它们的响应乱序返回，界面就在两个状态之间来回跳。

因此把「编辑」与「提交」分开：拨动只改浏览器内存里的草稿，底部浮出「保存 / 撤销」；保存时把所有改动合成**一条**请求一次写完，撤销或关闭面板即丢弃草稿。

代价是「拨了但没保存」成了一个用户必须能看见的状态，所以底部常驻一条 `N 处未保存` 的计数。

## 考虑过的替代方案

- **请求串行化 + 单调 seq**：能消除乱序，但每次拨动仍是一次全量往返，连点十次就是十次；失败还得逐条重试。
- **服务端合并窗口**（debounce）：把抖动推给后端，用户关掉页面时可能丢掉最后一次改动。
- **乐观 UI + 版本号**：需要客户端维护版本，复杂度和收益不成比例。

## 后果

- 在途请求数恒为 1，界面不会再被旧响应覆盖。
- 关闭弹层等于撤销：面板组件随之卸载，草稿自然消失，不需要额外清理。
- 分组增删改与「移动分组」**保持即时写入**。它们改的是跨工作区共享的组定义，放进草稿会让人误以为「撤销」能把它撤回。
- 预览必须在客户端重算一遍求值链（并带上草稿），否则打开一个分组后组内成员仍显示服务端的旧值，看起来就像开关没生效。
