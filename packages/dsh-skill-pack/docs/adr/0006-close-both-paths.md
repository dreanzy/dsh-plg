# 关闭 skill 同时关闭模型侧与用户侧

## 背景与决定

遮蔽副本最初只把 `modelInvocable` 置为 `false`，保留 `userInvocable: true`。这在 DSH 的词汇里是「仅用户」档：模型看不见、不能用 `skill` 工具加载，但用户手打 `/name` 时宿主仍会把全文注入上下文。开关因此名不副实——面板说关了，用户点名调用照常生效。

现在把两条标记都置为 `false`：

- 模型侧：`available_skills` 目录过滤掉它，`skill` 工具报 `not available for model invocation`。
- 用户侧：`agent/pre-step` 扫到 `/name` 后因 `!isUserInvocable` 直接 `continue`，不注入任何消息。

宿主对用户侧是**静默跳过**：`/name` 会作为普通文本发给模型，不给错误、不给提示。这条路径**不补任何客户端可见性**——试过的两处（输入框上方提示、已发送消息里的删除线 chip）都撤掉了：它们只在「名字存在但被关」这一个窗口里有意义，而用户对「关掉」的预期是「当它不存在」，提示反而把已关闭的名字重新带回视线。

## 考虑过的替代方案

- **维持「仅模型」**：开关名不副实，且用户无从知道「关了还能用」，比不做更糟。
- **拆成「模型可见」「用户可调用」两个独立开关**：求值链从「项级 + 组级」翻倍成两个维度，与 [ADR 0001](./0001-intent-writes.md) 的意图写入、[ADR 0002](./0002-groups-as-overlay.md) 的组级覆盖都要各写一遍；真实需求只有「全关」一种。
- **官方 `@deepseek-ai` 技能做例外，只挡模型**：按 skill 来源给语义分叉，宿主的两条检查路径却一视同仁；要做就得额外维护一份名单，收益不明。
- **本包注入一条「该 skill 已关闭」的说明消息**：监听器与宿主抢 `agent/pre-step` 的瀑布顺序，抛错会让整步失败，注入的 user 消息还会污染会话日志（标题、统计、导出都会把它当成用户原话）。

## 后果

- 依赖 `/name` 的既有工作流会失效。这是有意的语义变更：面板上的「关」从此只表示「两条路径都不通」。
- `/` 菜单会自动隐藏已关闭项：远端 `skills.list` 在返回前按 `isUserInvocable` 过滤，遮蔽副本到不了客户端。本包仍不能定制这个菜单（官方 source 独占 `("/", "skill")`），但也不需要定制。
- 遮蔽副本不再读正文（`skills.get()` 零调用）：正文在三条消费者路径上都在取之前被标记拒绝。`agent/created` 因此少了整段全量枚举。
- 复验判据从「`modelInvocable` 是否为 `false`」改成「两条是否都为 `false`」；只落一条也算关不掉。
