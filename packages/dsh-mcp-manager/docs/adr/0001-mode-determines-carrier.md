# 0001 三种模式的载体由模式决定

## 背景与决定

MCP 的工具怎么进上下文，本质是两件事：**什么时候建立连接**，以及**工具定义以什么形式占上下文**。可以拆成正交两维，也可以捆成一根旋钮。

决定：捆成一根旋钮。`eager` / `dynamic` / `lazy` 三档互斥，**模式决定载体**——`eager` 由宿主 `mcp-client` 整台挂载（无载体），`dynamic` 一律 `native`（原生注册），`lazy` 一律 `proxy`（不注册，经 `mcp_call` 转发）。用户不能单独选载体。

## 考虑过的替代方案

- **两维正交**（连接时机 × 暴露方式）：自由度最高，但把两个代价模型叠在一起后，用户遇到「想省 token 又不想牺牲启动速度」时反而无处可去——因为每一档的实际成本要自己推。而且 UI 会从三个单选变成两个选择器，认知负担翻倍。
- **只做两档**（`eager` + `dynamic`）：省掉代理通道的实现量，但 `dynamic` 每次加载都会让工具段变一次、请求前缀缓存失效。对长会话与多 server 是实打实的成本，没有 `lazy` 就没有低成本的替代。
- **让工具过滤规则决定载体**：曾经的想法——配了规则就把行从原生踢到代理。否决理由是它用一条**可见性**设置替用户改了**代价模型**，用户不读文档根本不知道。

## 后果

- `dynamic` 只有一条路径：连池里的连接 → 列工具 → 过滤 → 原生注册。不存在「整台走挂载、收窄走原生」这种同一模式两种代价的形态。
- 想省前缀缓存只能选 `lazy`，代价是多一层代理与更弱的绑定质量。
- `eager` 下工具过滤不生效：那条路由宿主整台挂载，本插件没有插手的点。
