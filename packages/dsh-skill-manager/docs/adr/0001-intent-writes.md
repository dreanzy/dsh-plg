# 策略变更提交绝对状态，不提交带版本的快照

## 背景与决定

面板每拨一次开关就是一次写入。沿用「提交整份策略 + 期望 revision」的乐观锁形状时，连续两次点击必然失败一次：第二次携带的 revision 在第一次写入后即过期，且它算出的整份策略里不含第一次的改动。锁在这种形状下无效——锁只保证不并发写，保证不了排队者的快照还有效。社区实现 dsh-skill-scope 的 `stale-revision` 报错即此。

因此改写入协议：每次变更提交一组绝对状态命令（`{层, 键, 值 | null}`），`null` 表示删键即回到跟随；服务端在文件锁内读—改—写，不做任何版本比对。命令满足三条性质——幂等（重复执行结果相同）、可交换（写不同键的顺序无关）、收敛（写同一键即后点者赢）——所以「冲突」不是一个可发生的结果。

revision 只留给整份替换（导入、恢复默认、清空本工作区），那类动作的语义本来就要求绑定一个基准版本。

## 考虑过的替代方案

- **保留 revision，客户端出队时再算新值**：重算需要「最新 revision」，而它只有在响应回来时才知道；两个在途请求仍基于同一个已返回版本，照样冲突，只是把并发压到 1。
- **客户端提交差量（add/remove 集合）**：`remove` 依赖当前状态，重放顺序敏感、不幂等，本质是意图的残缺表达。

## 后果

- 客户端不持有版本，没有「快照过期」这类状态需要刷新。
- 「跟随上层」只能表达为删键，写一个同值不等于跟随。因此落盘规则必须区分：用户显式做出的同向决定要保留，批量动作产生的同向值要剔除。
- 客户端仍需一个单调 seq 丢弃乱序返回的旧响应，否则连点时界面会回退。
