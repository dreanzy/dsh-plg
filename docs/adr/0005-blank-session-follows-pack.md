# 空白会话跟随 pack，开过轮次的会话不再动

## 背景与决定

「按工作区决定模型路由」与「不改写用户已经在用的会话」之间有冲突。原决定只写了一句"绑定只影响新开的会话"，落到实现时留了两个洞：

1. **模型位不刷新。** 面板保存后，已打开的空白会话仍显示旧 pack 的路由；用户看到的是"改了没反应"。
2. **判据分裂。** 施加模型用 `source === 'startup'`，判断"有没有内容"用 `request/header`，两套判据各自演化。恢复出来的会话（`resume`）即使从未发出请求，也永远拿不到 pack 的路由。

本决定把边界收成一条：**空白会话**。判据是会话事件里既无 `turn/start` 也无 `request/header`。空白会话在三个时点被重新施加路由——创建、恢复、用户切 pack；一旦开过轮次，任何时点都不再动。

## 考虑过的替代方案

### 用 `model/selection` 事件区分"用户手选"与"宿主初始选择"

做法：若历史里已有 `model/selection`，就当作用户选过，不再覆盖。

否掉的理由是事实不支持：宿主创建空会话时**总会**先写一条 `model/selection`（实测序列 `session → permission/preset → sandbox/mode → approval/policy → model/selection → agent/inbox/spliced → turn/start`，值是当时的默认模型）。按这条判据，所有新会话都有记录，pack 等于全线失效。事件本身也不带来源字段（`toSelection` 只产 `provider`/`model`/`reasoningEffort`），无从区分写入者。

### 插件自己记账：记住"我写过的值"，与记账不符就算用户改过

做法：内存里按 agent 记下每次施加的路由；发现当前选择不等于记账值，就认定是用户手选，跳过。

否掉的理由是记账活在进程里：DSH 重启后表清空，此时改 pack 对已存在的空白会话不生效——正好退回本决定要修的症状。为此把记账落盘，又要在会话之外维护一份与 `model/selection` 并行的状态，两份状态迟早打架，而收益只是保护一个"在空白会话里手选过模型"的边缘场景。

### 只在创建时施加，切 pack 时不重施加

做法：保持"只影响之后新开的会话"的字面语义。

否掉的理由是这恰好制造了用户报告的困惑：切 pack 是用户在面板上的显式动作，界面上什么都不变，只能理解为功能坏了。空白会话没有内容可损失，跟随新配置才是符合直觉的行为。

## 后果

- 空白会话里手选的模型会被覆盖（切 pack 或重新打开该会话时）。这是有意的取舍：空白会话的选择还没有产生任何内容，而切 pack 本身是用户的显式动作。
- 失败必须可见：重施加失败写入面板的「上一次施加失败」，否则用户会以为改成功了、模型却没变。
- 浏览器侧不需要任何额外通知：服务端写 `model/selection` → 服务端投影折叠 → Control Stream 推给客户端 → 模型位重渲染。
