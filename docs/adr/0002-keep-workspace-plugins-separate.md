# 三个按工作区裁剪的插件保持独立发行，只共享词汇

## 背景与决定

`dsh-skill-manager`、`dsh-plugin-manager`、`dsh-mcp-manager` 都在做同一类事：按工作区决定某样东西对模型是否可见。它们的管理对象不同——skill、插件的贡献（工具 + 提示词段）、MCP 的行——因此**决定不合并成一个包**：把工作区、层、跟随、覆盖、求值链、能力项这六个共有词提到根术语表，实现继续零共享，三者保持各自版本、各自发布、各自安装。

## 考虑过的替代方案

- **三合一**：重复的只有基础设施，约 150 行——`transact` 7 行、`readText` 8 行、`toResponse` 4 行、`readFetchFace` 9 行、`wrap`、前端 `post` 25 行、`T` 常量表，对三包合计 13672 行（`src` + `client` + `test`）而言约 1%。代价却是把 `@modelcontextprotocol/sdk` 与 `zod`、19 个测试文件（118 个用例，占三包测试量的一半）、`mcp-servers` 提示词段、`loader` 拦截和三个按需工具全部塞给只要管 skill 的人。`dsh-mcp-manager` 单是 `src` 就 3315 行，占三包 43%，是三者中最深的宿主耦合。
- **只合 skill + plugin**：两者连工作区 schema 都同为 `{ items, groups }`，是这条路上唯一干净的边界。仍然否掉：两者的单独升级价值真实存在（只想管 skill 的人不该被迫跟 MCP 的版本走），而合并换来的仍是那 150 行。
- **抽出共享包**：ADR 0001 已实测 `workspace:` 协议在用户从 git 子目录安装时不会被替换成真实版本，而是报 `ERR_PNPM_WORKSPACE_PKG_NOT_FOUND`。抽共享包在当前安装模型下不成立。
- **加一个薄聚合包**：不改三者、只做「一键装全套」。没有真实需求支撑，暂不做；真出现时它是一个只依赖另三者的包，不动这三者的边界。

## 后果

- 三包的工作区状态继续各自落在 `<cwd>/.dsh/<包名>.json`，全局状态各自落在 `$DSH_HOME/<包名>/`，互不干扰。
- 根术语表因此承担了「工作区」的权威定义，并记下它绕开 `ctx.workspaceRegistry` 的理由：注册表只收被显式命名过的少数目录，以 `WorkspaceId` 为键（移除后重加同一目录即换 id），需要 `dsh-session` 与整套存储组合才可用，且拒绝不存在的路径——而插件的开关必须对任意 cwd 生效。
- 三个面板已挂在同一组四个 UI 槽位上，`order` 为 40 / 41 / 42，「入口分散」不再是合并的理由。
- 容忍阈值：重复的基础设施与重复的词条，等**第四个** manager 出现再抽共享包；届时先解决 `workspace:` 或改为构建期生成，否则抽出来的包无法被源码安装的用户拿到。
- 待观察：`dsh-plugin-manager` 的「快照」（某个 agent 当前生效的集合）是否也是另两包共有的概念。目前只有它给这件事命了名。
