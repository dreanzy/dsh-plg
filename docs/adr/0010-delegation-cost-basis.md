# 委派成本按 total 判定，单次委派加 40 步软护栏

## 背景与决定

现象：子代理的 LLM 输出「偏高」，怀疑是插件要求子代理每约 8 次工具调用落一次检查点造成的。

实测反驳。取一次真实委派（四个深度 1 的子代理，日志逐帧解压后按 `assistant/message` 的 `usage` 汇总），按出现顺序记作 A–D：

| 子代理 | 步数 | output | 写检查点 | 占 output |
|---|---|---|---|---|
| A | 15 | 4,669 | 2 次 / 835 | 17.9% |
| B | 102 | 131,116 | 12 次 / 13,015 | 9.9% |
| C | 11 | 7,217 | 0 | 0 |
| D | 19 | 18,609 | 0 | 0 |
| 合计 | 147 | 161,611 | 14 次 / 13,850 | 8.6% |

三个数说明检查点不是主因：它占 output 8.6%，占 total 0.05%；四个子代理里有两个一次都没写；子代理每步平均 output（1,099）低于父会话（1,239）。

真正的大头在两个地方。一是单条长任务：B 一条 102 步吃掉 81% 的子代理 output，其 total 23.56M 里 cache 重付 22.98M（97.5%）。二是 PTC 生成的代码本身：交付物写入（`.tmp/<task>/*.json`）合计 49,911，占 output 30.9%，是检查点的 3.6 倍。

据此定三件事：

1. **判定口径改用 total**：委派贵不贵看 `totalTokens`（含 cache 重付），output 只用于判断「生成侧」是否异常。按 output 判会一直误把检查点、汇报段落当原因，忽略步数 × 上下文。
2. **加一条 40 步软护栏**：段里加 `Cap a single delegation at about 40 tool calls; past that, return what you have and let the parent decide whether to continue.`。40 是宽护栏不是目标值——实测正常任务 11/15/19 步，留两倍余量。
3. **检查点频率改成事件触发**：`every ~8 tool calls` → `when a conclusion lands or past ~15 tool calls`。频率不是成本源头，但「每 8 步固定要写」会诱导模型额外想一轮该写什么，那笔账在 output 里、不在这 13,850 里。

段文本 386 → 424 token（含四档表插入后的完整段），上限 400 → 450，spec §6.3 合计预算 600 → 650。

## 考虑过的替代方案

### 直接删掉检查点要求

否掉：它占 total 0.05%，删了只省零头，却拆掉子代理失败恢复的唯一机制——`AGENTS.md` 里只有路径约定、没有频率要求，段一旦不要求，全凭父代理每次在 prompt 里口头提。

### 工具层硬中断（到 40 步强制返回）

否掉：宿主 `startActivation` 的 request 只收 `prompt` / `agentOptions` / `parent` / `cwd` / `maxDepth`，没有步数键。要做硬约束得订阅子代理事件流自行计数、处理「正常收尾 vs 超限」的竞态，收益不抵复杂度。软约束配合父代理可以在返回后决定是否续派。

### 只压 output，不动口径

否掉：total 的 97.5% 是 cache 重付，压 output 等于在压零头；而真正的杠杆（长任务的步数）在 output 口径里看不出来。

## 后果

- 段预算 450，余 26 token 给措辞修订；工具描述仍留 200 的护栏。
- `prompt.test.js` 的 `/a checkpoint path/` 锚点在改写时保留，断言不需改。
- 软护栏依赖父代理执行：历史上的 102 步那条就不会被它拦住，它防的是下一次。
- 本 ADR 的基线（8.6% / 0.05% / 81%）可在同口径下复算，供将来复查：日志按 zstd 帧切分后逐条汇总 `data.usage`。
