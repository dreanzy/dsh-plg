# 用 pack 取代工作区层，四个领域各管各的名册

## 背景与决定

四个插件原本各有两层策略：全局层在 `$DSH_HOME/<包名>/`，工作区层在 `<cwd>/.dsh/<包名>.json`。后果是「同一批决定要在多个目录里重复维护」：五个美术项目要关同一批 skill，就得在五个 `.dsh/` 里各写一遍。

`dsh-model-scheme` 已经走到了另一条路上：全局存若干命名方案，工作区只存 `{ schemeId }`。本决定把这条路推广到全部四个领域，并把那个「命名方案」统一改称 **pack**。

三条具体决定：

1. **工作区层退役。** 求值链从「工作区项级 / 工作区组级 / 全局项级 / 全局组级」四环，收缩为「工作区绑定的 pack → default pack → 内置缺省」三环，且后两级都是 pack。工作区本身不再持有任何逐项决定。
2. **pack 是覆盖表，不是成员清单。** `Pack { name, items, groups }`，每个键三态：`true` / `false` / 不存在（跟随上一层）。不记录「这个包里有哪些项」。
3. **四个领域各有一套 pack 名册，互不可见。** 不做跨领域 pack，不合并四个包，不抽共享包——ADR 0002 的零共享继续有效。

## 考虑过的替代方案

### 一个跨领域的 pack（一个 pack 同时管 skill、插件、MCP 与模型路由）

做法：新建一个包持有统一的 pack 名册，四个领域都读它。

否掉的理由是 ADR 0002 已经量过的同一笔账：四个包合计一万三千行，共享的只有约 150 行基础设施；把「一个包都读同一份文件」这件事做出来，就要么抽共享包（`workspace:` 在源码安装下报 `ERR_PNPM_WORKSPACE_PKG_NOT_FOUND`），要么让四个包各写一遍同一份文件的解析与事务代码，而后者会立刻产生四种略有出入的读取实现。工作区绑一次 pack 确实更省事，但省下的这次点击，换来的是四个包之间新增一条隐式耦合。

### 每领域一套名册，但工作区可绑多个 pack

做法：`bindings: { cwd: [packA, packB] }`，按顺序合并。

否掉的理由是合并规则没有廉价答案。美术 pack 说某 skill 开、开发 pack 说关，谁赢？先到者赢要解释排序，后到者覆盖要让用户理解顺序，显式标冲突要再加一层 UI。而用户的真实诉求是「不要再逐个决定」，多绑把决定从逐个开关换成了排序问题，没有变简单。要混合就建第三个 pack。

### pack 是成员清单（包里列出哪些项，包外一律关）

否掉的理由有两条。一是新装的 skill 在旧 pack 里默认消失，用户得知道去哪个包里补一条，而「为什么刚装的东西看不见」是最难自诊断的一类问题。二是它无法表达「这一项跟随默认」——包外全关是个更强的断言，用不了 `??` 链。

### 保留工作区层，pack 只作为「批量应用」的宏

做法：pack 是模板，应用时把值写进各工作区的 `.dsh/`。

否掉的理由：模板一旦应用就与模板脱钩，改 pack 不影响已经应用过的工作区。用户会预期「我改了美术 pack，五个美术项目应该一起变」——这正是他要 pack 的原因。

### 保留工作区层，求值链加一环

做法：`pack.items ?? pack.groups ?? global.items ?? global.groups ?? true` 之外，工作区层仍可压过 pack。

否掉的理由：那等于留一个绕过 pack 的后门，「工作区只绑 pack」的承诺当场失效，而且用户仍要理解两套机制。

## 后果

- **旧数据必须迁移。** 每个曾有过 `<cwd>/.dsh/<包名>.json` 的工作区，会生成一个同名 pack 并自动绑定。这是本决定最重的一次性成本，迁移脚本必须只读旧文件、只写新文件，删除动作单独成步。
- **全局层消失，改由 `default` pack 承担。** 它可编辑但不可删除、不可改名。原来 `global.json` 的 `items` / `groups` 直接搬进去，语义不变。
- **工作区目录下不再产生任何状态文件。** `.dsh/` 从「插件状态」退化成「可选的用户配置」。
- **MCP 补上分组。** 它原本没有组，而「分包」页要在三个领域统一出现，逐个挑 `own:foo` / `global:bar` 这种机器键最容易漏。组级只给一个布尔，四字段（`enabled` / `mode` / `tools` / `description`）只留在行级——组级设 `mode` 会立刻撞上「组说 dynamic、行说 disabled」的合并问题。
- **工作区清单取自宿主会话**（`ctx.remote.session.list()` 的 cwd 去重），插件不再自建目录记录。代价是只显示有过会话的目录，从未开过会话的目录要手动加一条路径。
- **`scheme` 这个词退役。** `dsh-model-scheme` 改名 `dsh-model-pack`，方案、分包、pack 在四处文档里统一成一个词。

## 何时重新考虑

- 官方给出「工作区维度」的配置原语（例如 `agentDefaultModel` 变成可分层，或插件状态有宿主托管的 per-workspace 存储），四个包各自维护 `workspaces.json` 与 cwd 规范化就都是重复劳动，可以整体退役。
- 四个领域出现「必须一起改」的配置（例如某个 pack 的 skill 与 MCP 天然成对），跨领域 pack 才有真实需求；届时先解决共享代码的安装问题，再谈合并。
- 用户明确需要「工作区绑多个 pack」且能给出无歧义的合并规则时，重开第三条的决定。
