# 待保存改动：先试算，点「保存」才写盘

## 背景与决定

四个 pack 插件的面板原先都是「点一下即写盘」：开关、绑定、改名都直接发 `apply`，等服务器返回整车视图才刷新。由此有三个反复出现的抱怨：

1. 界面会重排序。列表按名字与三态排序，改个名或拨个开关，行就跳到别处，下一次点击落在别的行上。
2. 响应慢半拍。中间是「请求 → 写文件 → 重新读 → 重算求值」的整趟往返，没有任何即时反馈。
3. 容易误操作。没有确认、没有撤销，一次误点就是一次落盘。

本决定把写盘时机从"点控件"挪到"点保存"：

- 点控件只把命令放进**待保存队列**，不发写请求。
- 队列非空时，每一步都用 `dryRun` 让服务端**试算**一次，返回与真写完全同一种视图；面板按这份视图渲染。
- 底部常驻一条**确认条**：左「已改 N 项」，右「撤销 / 放弃全部 / 保存」。保存才把整批命令作为一次 `apply` 写盘。

队列活在这一次面板挂载里：关闭面板、切会话、刷新即丢。

## 考虑过的替代方案

### 乐观更新 + 立即写盘 + 只提供撤销

做法：改动照旧立刻落盘，浮条只给「撤销」，撤销时发一条逆命令。

否掉的理由不全在成本，而在两类操作的性质不同。开关、绑定、改名都可以发逆命令撤回去；`deletePack` / `deleteGroup` 是**硬删**，还顺手清掉指向它的绑定与各 pack 里的组开关（`src/store.ts:446`），撤销只能重建，而重建出来是新 id——分组 id 一变，pack 里按 id 引用的组级开关就全断了。于是"撤销"能力天然分裂成两档，比在入口处统一延迟提交更难解释。

### 浏览器本地重算视图

做法：把 22 个 `op` 的应用逻辑写进 `client.js`，改完自己算出新视图。

否掉的理由是它直接违反根术语表的「生效视图」：装配路径与面板读同一份答案，浏览器只把原始记录拼成显示态，**不再自己走一遍求值链**。四个包各有独立求值链（skill 有四环、mcp 逐字段、plugin 四环、model 一条），照抄一份等于把四条链变成八条，且必然与宿主侧漂移。

### 删除也进队列

做法：删除与其它改动同住一个队列，保存时一起提交。

否掉的理由是它会变成三次点击（点删除 → 确认删除 → 保存），而且中间态的语义是坏的：行已经从界面上消失，磁盘上却还在。删除的真实语义是"不可逆"，用二段确认表达就够了。

### 未保存改动跨面板保留

做法：队列放在模块级 store 里，关掉面板再打开还在。

否掉的理由来自使用现场：关掉面板过一阵再回来，用户已经不记得点过什么了。留着比丢掉更让人困惑——"它是不是已经生效了？"

## 后果

- 每个控件点击多一次本地回环请求（`dryRun`），这是"立刻看到结果"的代价；命令是绝对状态、幂等，重复试算不会累积副作用。
- 未保存改动会随关面板丢失，且**没有**"有未保存改动"的拦截提示。取代它的是确认条的计数与行首的竖条：只要队列非空，面板底部就一直有东西在提醒。
- 面板内显示待确认值，面板外（chip 上的 pack 名）始终显示真实值——不能让人以为已经生效。
- 待保存期间冻结排序：位置按改动前的那份视图，保存后才按新值重排。归属变化（行换组）不冻结，因为那是用户动作本身的后果。
- 删除仍然当场生效、不可撤销；界面用「确认」+ 浅红底把它和队列里的待保存状态区分开。
- 冻结排序是「沿用改动前的排序键」，不是「按改动前的数组位置」。两者不等价：列表按名字排，数组位置却是按 id 排，用后者会在一进入待保存状态时反而重排一次。

## 四个包的落地差异

决定对四个包一致，实现各有三处不同，都记在各包代码注释里：

- **求值链**：skill-pack 四环（项级/组级 × 两 pack），plugin-pack 同构，mcp-pack 逐字段独立（`enabled` / `mode` / `tools` / `description` 各走各的），model-pack 没有开关表、只有路由。试算因此必须各自复用自己的应用函数，不能共用一份。
- **能力差异**：model-pack 原先就有一套草稿模型（路由/档位/提示词），这次并入队列后**不再有第二个提交入口**；mcp-pack 多一层托管 MCP 定义的增删（走独立 `/servers` 路由、当场写盘），删除前要把引用该行的待保存命令剔掉；plugin-pack 的受保护插件保留弹窗式确认，确认后同样只入队。
- **命令粒度**：model-pack 的 `putPrompts` 是「只带改过键的补丁」，按单键去重会丢别的键，所以它对队列不做键级去重；其余包按目标键去重。
